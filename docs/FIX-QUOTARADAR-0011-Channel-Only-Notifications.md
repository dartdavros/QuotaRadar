# Уведомления о квотах только в канале

Решение владельца от 13 ноября 2026: прекратить личные уведомления немедленно после
внедрения и один раз известить всех сохранённых личных получателей, до которых
удастся доставить сообщение, включая отключивших подписку через `/stop`.
Канал: https://t.me/quotaradar.

Этот документ заменяет требования о личных подписках в ARCH-0001 §2.2, §6.6,
SPEC-0001 FR-010, FR-011 и критерии 12, а также соответствующие пункты PLAN-0001.
Новостное направление и сообщения в группы не меняются.

## Поведение

- Новые quota-доставки создаются только для активных целей `channel`.
- Задачи отправки отказываются отправлять quota-события в `private_chat`, даже
  если старый target вручную включили или задача уже находилась в Redis.
- Восстановление очереди и ручной повтор не возвращают личные доставки в работу.
- `/start`, `/stop`, `/status` в личном чате отвечают утверждённым объявлением.
  Подписки не создаются и не включаются; группы и каналы игнорируются.
- Миграция `telegram.0005` отключает личные targets и переводит их `pending`
  доставки в `failed` с причиной прекращения уведомлений. История `sent`,
  `failed`, `uncertain`, получатели, группы и каналы сохраняются.
- Откат миграции не включает старые подписки обратно.

Утверждённое сообщение:

> Уведомления о сбросах лимитов Codex и Claude Code больше не будут приходить в личные сообщения через бота.
>
> Теперь все уведомления публикуются только в канале QuotaRadar: https://t.me/quotaradar
>
> Подпишитесь на канал, чтобы получать новые уведомления.

## Разовое объявление

`python manage.py announce_private_retirement` показывает текст, число личных
получателей и итоговые статусы. Без `--send` команда только читает БД, не создаёт
журнал и не обращается к Telegram.

`python manage.py announce_private_retirement --send` отправляет сообщение через
штатный Telegram-клиент с существующими токеном и настройками прокси. Отбираются
все `private_chat` с положительным числовым ID независимо от `enabled`.
Отрицательные ID групп/каналов дополнительно исключены.

Для каждого получателя создаётся единственная запись `PrivateChatRetirementNotice`.
Перед HTTP атомарно фиксируется `sending`, после подтверждения — `sent`, message ID
и время. Повторный/параллельный запуск не захватывает такую запись второй раз.
Недоступные чаты получают `unreachable`; отправка следующим пользователям продолжается.

Скорость одного процесса ограничена десятью запросами в секунду. Подтверждённый
отказ по rate limit возвращает запись в `pending` с `next_attempt_at`. Команда
ждёт указанный Telegram срок и делает до трёх попыток на получателя за запуск;
при продолжающемся ограничении останавливается. Её можно запустить повторно.
Запускать один процесс рассылки, чтобы соблюдать общую скорость бота.

Ошибки токена/конфигурации останавливают рассылку. После исправления настройки
допустим повторный запуск: подтверждённо не принятый запрос остаётся `pending`.

Timeout, ответ без message ID или другой неоднозначный сетевой исход фиксируется
как `uncertain`. Аварийно прерванная отправка остаётся `sending`. Эти записи
автоматически не повторяются: Telegram не предоставляет idempotency key для
`sendMessage`, поэтому невозможно одновременно гарантировать отсутствие дублей
и доставку после неизвестного исхода. Требуется отдельная проверка владельцем;
не сбрасывать статусы массово. Итоговая сводка явно показывает эти количества.

## Порядок production-внедрения для согласования

1. Сохранить резервную копию БД и текущий образ; использовать существующий
   deployment `/opt/quotaradar` и штатный порядок обновления с сохранением runtime.
2. Собрать новый образ и проверить конфигурацию. Штатно остановить runtime-сервисы
   с ожиданием завершения текущих задач, чтобы старый worker не отправлял личные
   сообщения во время миграции.
3. Применить миграции через `init`, запустить runtime-сервисы с новым кодом.
4. Проверить здоровье сервисов, отключённые private targets, отсутствие личных
   `pending` quota-доставок и сохранность действующих каналов.
5. Выполнить preview, затем `--send` и сохранить итоговую сводку.

Перед любыми изменениями production владелец должен отдельно согласовать точный
план и версию пакета. Миграция и обычный деплой сами по себе объявление не отправляют.

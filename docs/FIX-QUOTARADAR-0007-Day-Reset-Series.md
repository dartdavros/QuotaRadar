# Объявления Day N / Reset без зависимости от LLM

Владелец согласовал реализацию и выкладку 15 октября 2026.

## Требование

Посты `Day 6/ Reset`, `Day 8/ Reset` и объявление дня 10 с вступлением автора
должны распознаваться как `quota_reset` независимо от ответа или доступности LLM.

## Реализация

- Правило привязано к стабильному X author ID `1953337039510003712`, провайдеру
  OpenAI, сохранённому X User ID источника, author ID и ID основного поста в raw API.
  Одного username недостаточно. Ретвиты исключены.
- В собственном тексте должна быть ровно одна отдельная строка `Day N/ Reset`
  с положительным номером дня. Пробелы и регистр несущественны.
- Родительский пост, цитата или упоминание в includes не активируют правило.
- Вопросы, отрицания, Git/API/настройки/отдельный аккаунт, примеры, отмена,
  неоднозначные несколько дней и явное указание будущего времени не публикуются
  автоматически этим правилом; для них сохраняется путь обычного анализа.
- Текст совпадает с ранее утверждёнными ручными публикациями:
  `🟢[CODEX] Использованные лимиты сброшены` и
  `Объявлен сброс лимитов Codex — день N.`
- Анализ получает модель `rule/thsottiaux-day-reset-v1` и audit с ID правила,
  автора, поста и номером дня. Настройка и версия активного промпта не меняются.
- Сохраняются штатные блокировка анализа, транзакционное сохранение, проверка
  текста, fan-out, ограничение свежести и дедупликация доставки.
- Правило не меняет счётчик доступности LLM и работает без её конфигурации.
- Для других reset-постов подтверждённого автора отрицательный результат
  перепроверяется без обязательных слов массовости и квоты. Для остальных
  источников критерии перепроверки сохранены.
- Неразрешённая повторная оценка остаётся `failed` с причиной и raw responses.
- Уже завершённые анализы, включая ручные публикации, автоматически не пересматриваются.

## Проверка и выкладка

Используется штатный Docker test-сервис с PostgreSQL и Redis. Проверяются реальные
форматы дней 6/8/10, неподтверждённые ID, цитаты, отрицания, технические сбросы,
работа без LLM, однократная постановка доставки, старые посты и сохранение ручной
публикации. Миграции БД, изменения UI, volumes, доступов и Telegram-доставки не нужны.

Production-процедура повторяет согласованную выкладку в `/opt/quotaradar`:
резервные копии исходников, БД и image; замена только файлов исправления;
сборка image; Django check; штатная остановка шести процессов приложения;
сохранение и восстановление прежних runtime-файлов; запуск и проверка здоровья.
PostgreSQL и Redis не останавливаются. Проверка старых объявлений выполняется
без записи новых анализов и без повторной отправки сообщений.

## Результат выкладки

- Docker-сборка и 45 целевых тестов прошли. `makemigrations --check --dry-run`
  подтвердил отсутствие изменений схемы. Изменённые файлы проверены на размер
  и разделение ответственности; UI не изменялся.
- На `138.124.109.186` заменены пять файлов приложения. SHA256 каждого файла
  внутри работающего web совпал с локальным manifest.
- Все шесть процессов приложения работают на image
  `sha256:ae79775cf55cdd134b848b18f15d65035893e2c18976846d598be792e143b24c`,
  число рестартов — 0; web healthy. Django check прошёл, HTTPS admin возвращает
  ожидаемый 302 с успешной проверкой TLS.
- В read-only транзакции на реальных постах 2038, 2068 и 2106 проверено
  распознавание дней 6/8/10 без LLM. Для поста 2069 подтверждено включение
  перепроверки без слов квоты.
- Ручные анализы и существующие доставки с message IDs 94, 96, 98 сохранены.
  Автоматического backfill и повторных отправок не было. Промпт остался v4.
- Резервные копии исходников, БД и runtime-файлов находятся в root-only каталоге
  `/opt/quotaradar/backups/deploy-day-reset-series-20261015-01a127ea/`.
  Прежний image сохранён как `quotaradar:before-day-reset-series-20261015-01a127ea`.
